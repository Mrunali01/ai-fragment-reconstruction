## C. Code walkthrough

### Moving and saving pieces

The canvas stores a 25-entry array of upload indices. A move copies the array and
swaps two entries; it never creates or deletes a piece. A bounded undo list stores
previous arrays. Tiles display the corresponding region of the original solver
PNG, so independent original upload files are not needed after a reload.

Saving posts the array and note to FastAPI. `CorrectionInput` accepts strictly
integer indices and validates the exact permutation 0?24. The server crops the
base PNG according to its original placement metadata, pastes those pieces into
the new order, writes a new UUID-named PNG and persists a new version record.
The original result is never overwritten. Version downloads use the selected
saved version; unsaved edits must be saved first.

### Running work in the background

`JobRunner` owns one executor thread and permits at most two outstanding
background jobs. Computation shares the existing lock with the legacy synchronous
endpoint, so only one reconstruction runs at a time. Excess submissions return
429 with Retry-After. Inputs are validated before acceptance. The job is persisted
before it is scheduled; worker transitions are persisted as they happen.

The browser polls every 500 ms. The URL initially contains `?job=UUID`, then
changes to `?result=UUID` on completion. There are no invented progress percentages.
Graceful shutdown drains accepted work. On startup, queued/running records left
by an interrupted process are marked failed with a resubmission message. The
input pieces are not persisted, so interrupted work cannot automatically resume.
Use one API process/worker per database and result root; this is a local worker,
not a distributed job queue. There is no cancellation or automatic retry yet.

The original `POST /reconstructions` continues to run synchronously and returns
201. Both paths call the same execution function and frozen solver. ML parameters,
training splits and evaluation settings were not changed.

### Evidence and analytics definitions

For each of the 40 RIGHT/DOWN placed borders, the report compares the selected
neighbor against all 24 non-self candidates. Rank is `1 + number of alternatives
with strictly lower cost`; tied candidates share rank. The normalized margin is
`(best alternative cost - chosen cost) / (abs(best alternative cost) + abs(chosen cost) + 1e-12)`.
A negative margin means an alternative scored better locally; zero includes ties.
The best three alternatives are retained for inspection.

The fraction of placed borders tied for best local score is **not neighbor
prediction accuracy**. True neighbor accuracy needs ground truth. Raw classical
RGB costs and normalized CNN costs are not directly comparable across scorers.
The heat tint uses each piece's weakest incident margin: green above 0.05, orange
otherwise. This display cutoff is a visual heuristic, not learned calibration.
The tint disappears after a manual rearrangement because stored evidence describes
the original solver layout. Human corrections are never silently given its scores.

History compares uploaded-file hash multisets before enabling two-attempt
comparison. Position differences compare the file hashes in corresponding grid
slots. Duplicate or differently encoded but pixel-identical files can make
content/identity interpretation ambiguous; this is not a correctness metric.
Human version comparisons count moved upload indices, also not accuracy.

Analytics counts actual stored results, correction versions, corrected result
IDs, scorer/search choices and background job states. Processing duration is
measured with a monotonic clock from execution start through scoring/diagnostics;
it excludes queue wait, upload and final result file/database writes. Older
results without recorded durations are excluded from the mean and its denominator
is displayed. These local timings mix methods and are not a controlled benchmark.
Without supplied ground truth, position accuracy and exact reconstruction rate
remain null. The earlier Phase 8 offline evaluation remains the source of actual
held-out reconstruction accuracy.

| Endpoint | Behavior |
| --- | --- |

| `GET /jobs/{job_id}` | Persistent queued/running/completed/failed state and completed result ID or error. |
| `GET /jobs?limit=10&offset=0` | Recent jobs, paginated, maximum limit 100. |
| `POST /reconstructions/{id}/corrections` | Save `{order: [25 upload indices], note: optional string}` as a new version; returns 201. |

| `GET /reconstructions/{id}/corrections/{version}/image` | Retrieve the selected saved correction PNG. |

| `GET /reconstructions/{id}/export?format=json\|csv\|zip` | Original arrangement report/download. |

ZIP contents are `reconstruction.png`, `arrangement.csv` and `metadata.json`.
CSV uses row/column, upload index, filename and SHA-256; potentially formula-like
filenames are prefixed with an apostrophe for spreadsheet safety. JSON explicitly
states that ground truth is unavailable and evidence concerns the original solver
arrangement. Correction exports do not claim that human edits are correct.

## E. Decisions and remaining limitations

The app still accepts complete, upright 5 ? 5 puzzles of RGB 64 ? 64 PNG/JPEG
pieces. It does not support arbitrary shapes, rotations, missing pieces or an
arbitrary piece count. It estimates arrangements and does not guarantee success.

PostgreSQL is authoritative when configured; filesystem-only mode persists
workspace records as atomically replaced JSON under `artifacts/api_results/workspace`.
Images stay on disk and require backup alongside the database. Schema 1?2 adds
workspace records without discarding existing results.

Files and PostgreSQL cannot share an atomic transaction. A crash can leave orphaned
images, an incomplete legacy job or even a completed result in history before its
background job records completion. Interrupted background states are marked failed
on restart; a surviving result can still be opened from history. Handled failures
clean newly created files where possible. No crash recovery/replay of input pieces
is promised. Human versions persist and originals remain available.

History uses limit/offset pagination; concurrent new attempts can shift page
boundaries. Analytics currently reads local stored metadata in memory and its
queries are not a single snapshot across tables. It is suitable for this project
scale; large deployments need database aggregation, stronger worker coordination,
retention and access control. There is no authentication or multi-worker/distributed
queue support. These phases did not deploy or publish the application.

## Follow-up: reconstruct after manual shuffling (2026-10-20)

The manual grid is intended to correct erroneous solver placements. Its original
reset control restored the previous result, but there was no way to submit the
edited grid to the solver without selecting files again. That gap is now fixed.

- **Restore solver result** replaces the ambiguous reset label and restores the
  previous arrangement instantly, without inference.
- **Reconstruct again** accepts the current grid order and optional method/search
  choices, submits a fresh background job, and opens its new result. No upload is
  required, including after a page reload. Manual placements are not locked.
- The server recovers the original decoded RGB pixels from the lossless result
  PNG. It reorders them using the validated current permutation and retains
  original filenames/file hashes as upload provenance. New job/result metadata
  records `source_result_id` and `source_order`; older results remain readable.
- The original result and saved correction versions are preserved in history.
  Save edits first to keep the manual layout itself as a correction. Rerunning
  the same method may return the same arrangement and does not imply improvement.
- A rejected rerun preserves the edited grid and enables retry.

Changed components: new `ReconstructAgain.tsx`, `PuzzleCanvas.tsx`,
`CorrectionWorkspace.tsx`, shared frontend API types and feature browser tests.
Backend changes: `workspace_routes.py` adds the reconstruct endpoint and reusable
pixel recovery, `background_jobs.py` carries provenance, and `api.py` plus
`api_schemas.py` persist it. `tests/test_workspace.py` checks pixel identity,
permutation validation, unavailable models, missing/incompatible images and
non-destructive reruns. README/API/frontend documentation is updated.

Full-suite testing exposed a Windows file-access race when polling filesystem-only
job records during atomic replacement. `WorkspaceStorage.get()` now shares the
writer's lock, preventing that same-process read/write overlap. PostgreSQL-backed
browser reruns also passed. This remains a single-process local worker design.

Final follow-up verification: full Python suite **122 passed in 57.99 seconds**
with PostgreSQL tests enabled; browser suite **9 passed in 20.8 seconds**; Next.js
production build, TypeScript checks, `pip check` and `git diff --check` passed.
The browser additions verify that the edited order reaches the real rerun API,
a fresh result records the correct source, and a queue rejection preserves edits.
No commit, push, model retraining or new reconstruction-accuracy claim was made.

Visibility follow-up: the green **Reconstruct again** button now lives directly
inside the grid's action row beside Undo/Restore. Solver settings are available
under **Solver options** there. Browser coverage scopes the rerun action to the
interactive grid so it cannot regress into an unrelated section farther below.

UI simplification: removed the “Your reconstruction activity” panel at the user's
